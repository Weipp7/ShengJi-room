# Shengji Long-Term Iteration Plan

## 目标

建立文档驱动的长期工程迭代流程，让后续功能补齐、代码修改、测试验证、评审和回滚都能从 `docs/iteration/` 追溯。

## 事实基础

- Monorepo：`apps/web`、`apps/server`、`packages/shared`、`packages/game`、`packages/bot`。
- 前端：React 18 + Vite + TypeScript，入口 `apps/web/src/App.tsx`，全局状态在 `apps/web/src/store.tsx`。
- 服务端：Express + Socket.IO，入口 `apps/server/src/app.ts` / `index.ts`，房间状态在内存 `RoomManager`。
- 规则：`packages/game/src/round.ts` 是 round 状态机，`bidding.ts` / `follow.ts` / `trick.ts` / `scoring.ts` 分别处理叫主、跟牌、墩判定、结算。
- 机器人：`packages/bot` 做叫主/埋底/出牌决策，`apps/server/src/botRunner.ts` 负责延迟调度。
- 当前分支已建立多个可回滚检查点，已完成亮庄/反主扩展、庄前/庄后反牌、机器人亮庄策略、规则边界测试、甩牌惩罚和机器人埋牌策略。
- 最新完整验证记录在 `docs/iteration/test-report.md`：`pnpm test` 26 文件 210 测试通过、`pnpm typecheck` 通过、`pnpm build` 通过。

## 阶段拆分

### Phase 0：基线收敛

目标：冻结当前工作树事实，决定上一轮改动如何提交/拆分/回滚，建立后续迭代检查点。

输出：

- `ITER-000` 完成。
- 明确当前分支是否提交、拆分 PR、或继续作为工作分支。
- `docs/iteration/decision-log.md` 记录基线决策。

### Phase 1：玩家操作可靠性

目标：优先处理会直接伤害试玩信任的问题：重复点击、错误反馈消失、收墩驻留误解。

顺序：

1. `ITER-001` 快速/重复操作的幂等与可理解错误反馈。
2. `ITER-004` Bot 调度竞态和取消测试。
3. `ITER-007` 收墩驻留体验。

### Phase 2：亮庄/反主规则扩展

目标：支持用户新增的任意张数亮庄、大小王反主、庄前反牌、庄后反牌，并保持 UI 文案、状态机和测试一致。

顺序：

1. `ITER-013` 任意张数亮庄、大小王反主与亮牌强度模型。
2. `ITER-014` 庄前反牌与庄后反牌阶段。
3. `ITER-010` 机器人亮庄与反主策略升级。

### Phase 3：甩牌与结算规则

目标：支持甩牌、失败惩罚和可审计结算，避免玩家看到的墩归属、扣分和总分不一致。

顺序：

1. `ITER-005` 规则边界与结算端到端测试补齐。
2. `ITER-016` 甩牌功能与失败惩罚结算。

### Phase 4：机器人与出牌辅助

目标：升级机器人埋牌、领牌、跟牌策略，并把同一评估能力暴露为玩家可理解的出牌提示。

顺序：

1. `ITER-011` 机器人埋牌策略升级。
2. `ITER-012` 高级机器人领牌与跟牌策略升级。
3. `ITER-015` 出牌提示按钮与可解释推荐。

### Phase 5：验证基础设施

目标：把目前临时浏览器脚本沉淀成仓库内可重复 E2E，支持多客户端、固定牌序、响应式截图。

顺序：

1. `ITER-002` 确定性 E2E 与多客户端浏览器验证基础设施。
2. `ITER-008` 重连、旁观、多标签与离线状态恢复验证。

### Phase 6：可达性与布局

目标：让真实玩家在键盘、触屏、小屏、聊天打开、长昵称等条件下仍能完成牌局。

顺序：

1. `ITER-003` 卡牌操作无障碍。
2. `ITER-006` 响应式、聊天抽屉和长昵称布局硬化。

### Phase 7：持续缺陷池

目标：把新增功能引出的 bug、体验异常和回归风险统一记录、分类和修复。

顺序：

1. `ITER-017` 扩展功能缺陷池与回归修复流程。

### Phase 8：发布硬化

目标：让部署、日志、回滚和验收流程可以被重复执行。

顺序：

1. `ITER-009` 发布、部署和回滚证据规范化。

## 通用执行循环

每个功能严格执行：

1. 阅读对应 `docs/iteration/NNN-*.md`。
2. 阅读涉及代码和已有测试。
3. 写失败测试或可复现脚本。
4. 运行目标测试确认失败。
5. 实现最小代码变更。
6. 运行目标测试确认通过。
7. 运行受影响的集成/浏览器验证。
8. 更新功能文档、`todo.md` 状态和 `decision-log.md`。
9. 运行 `pnpm test`、`pnpm typecheck`，必要时运行 `pnpm build`。
10. 记录回滚方式。

## 全局风险

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| 当前分支有未提交历史改动 | 后续变更难以回滚和 review | 先做 ITER-000，建立基线 checkpoint |
| E2E 仍靠临时脚本 | 试玩 bug 容易回归 | ITER-002 前置于大型 UI 改动 |
| 规则变体未完全决策 | 可能修出不符合玩家预期的规则 | ITER-005 先锁定现状并记录决策 |
| UI 小屏/聊天/长昵称缺自动覆盖 | 视觉回归靠人工发现 | ITER-006 纳入截图和 DOM 断言 |
| 服务端内存状态 | 重启清空房间，无法恢复生产牌局 | ITER-009 明确 MVP 限制和上线要求 |
| 新增规则互相依赖 | 亮庄、庄后反牌、甩牌、bot 策略可能互相污染 | 先做 ITER-013/014/016 的规则测试，再接 UI 和 bot |
| Bot 策略过拟合测试牌例 | 看起来聪明但真实牌局不自然 | 用固定场景和随机回归双轨验证 |
| 出牌提示可能破坏玩家自主性 | 提示像“标准答案”，玩家不理解原因 | ITER-015 必须展示推荐理由和可选性 |

## 文档更新要求

- `todo.md`：状态、优先级、依赖变化。
- `decision-log.md`：规则、范围、测试策略、回滚策略的取舍。
- 对应功能文档：执行记录、测试命令、结果、失败和修复。
- 如产生截图或日志证据，写入功能文档的“验证证据”。

## 当前阶段边界

文档阶段完成后，先提交当前 worktree 作为基线，再按 `todo.md` 顺序执行。后续每项功能必须先补测试或复现脚本，再改业务代码。
